# Task 1.3 — Researcher chat (MVP-0)

## Goal and context

Эта спецификация описывает только задачу 1.3 из roadmap AI Studio — чат с AI-аналитиком на экране Researcher, в варианте MVP-0. Задача доставляет основной пользовательский путь: пользователь пишет сообщение → ответ аналитика стримится обратно через SSE → диалог сохраняется в схеме проекта.

Что входит в объём:

- UI чата (центральная панель: список сообщений, поле ввода, кнопка отправки) и левая панель с артефактами проекта (декоративные/заглушечные элементы — без логики генерации и загрузки).
- API-маршрут `POST /api/projects/[id]/chat` со стримингом ответа через Server-Sent Events.
- Адаптер ModelRouter в `packages/ai-roles` с интерфейсом, поддерживающим несколько провайдеров; в MVP-0 поставляется одна реализация — гибридный провайдер z.ai.
- Чтение системного промпта аналитика из `.claude/agents/analyst.md` в рантайме.
- Сохранение истории диалога в модели `ChatMessage` (с новыми полями `tokensIn`, `tokensOut`).

Что НЕ входит (более поздние задачи):

- Генерация SPEC.md и кнопка «Create specification» — только UI-заглушка без логики (Task 2.1).
- RAG-индексация загруженных файлов и подмешивание фрагментов в контекст (Task 2.1).
- Загрузка файлов в MinIO (Task 2.1).
- Экран настройки ModelConfig — выбор провайдера/модели и ввод API-ключей через UI (Task 2.3).
- Логика fallback-цепочки и кеширование запросов — интерфейс их закладывает, но MVP-0 их не реализует.
- Правая панель с превью SPEC.md — нечего превью, генерации ещё нет.

Для кого: все аутентифицированные пользователи (оба режима UI — basic и professional). Чат — первичный экран в basic-режиме после создания проекта.

## Users and roles

Экран доступен одному типу пользователя платформы — аутентифицированному владельцу проекта. Проверка через `requireUser()` (сессия) и `canAccessProject(userId, projectId)` (владение). Режим UI (`BASIC` / `PRO`) на объём Task 1.3 не влияет — обеим режимам доступен одинаковый чат. Роли `ADMIN` / `OWNER` в MVP-0 не задействованы.

(Роли, относящиеся к платформе в целом, описаны в `specs/ai-studio/SPEC.md` и здесь не повторяются.)

## Functional requirements

### Screen/Page "Researcher" (вариант MVP-0)

- **URL**: `/projects/[id]/research`
- **Available to roles**: все аутентифицированные пользователи, владельцы проекта.
- **Purpose**: интервью с AI-аналитиком. В варианте 1.3 — только чат и навигация по артефактам; генерация спецификации, загрузка файлов и превью SPEC.md отсутствуют.
- **Interface elements**:
  - [List] Левая панель (~20%) — артефакты проекта. Содержит:
    - [Text] «Спецификация» с номером версии. В MVP-0 версии ещё нет — отображается заглушка «Спецификация не создана».
    - [List] «Загруженные файлы». В MVP-0 загрузка не реализована — список пуст, отображается «Нет файлов».
    - [Link] «Дорожная карта» → `/projects/[id]/tasks`.
  - [Button] «Создать спецификацию». В MVP-0 — UI-заглушка: кнопка присутствует в макете, но не запускает генерацию. Поведение: нажатие ничего не делает (или показывает toast «Генерация спецификации будет доступна позже»). Реальная логика — Task 2.1.
  - [List] Центральная панель (~80%) — история сообщений чата. Каждое сообщение: аватар (AI/пользователь), текст, временная метка. Сообщения аналитика и пользователя визуально различимы (выравнивание, цвет аватара).
  - [Input] Поле ввода сообщения (многострочное, отправка по Enter / Ctrl+Enter — на усмотрение реализации).
  - [Button] «Отправить» — отправляет сообщение пользователя.
- **States**:
  - `loading` — индикатор «печатает…» («Аналитик печатает…») во время ожидания и стриминга ответа; поле ввода и кнопка отправки блокируются до завершения стрима.
  - `empty` — сообщений ещё нет, отображается приветственное сообщение аналитика или подсказка «Опишите идею вашего приложения».
  - `error` — «Что-то пошло не так, попробуйте ещё раз». Частичный ответ, полученный до обрыва стрима, остаётся видимым в текущей сессии, но не сохраняется (см. Logic).
  - `streaming` — текст ответа появляется по мере получения чанков от сервера; скролл автоматически следует за новым текстом.
- **Logic**:
  - Начальная загрузка: серверный компонент страницы читает историю диалога через сервисный слой (`listMessages`) напрямую из проектного Prisma-клиента — по паттерну существующего `getProject` (FSD: страница → feature-сервис → `@aiflow/db`).
  - Отправка сообщения: клиентский компонент выполняет `POST /api/projects/[id]/chat` с телом `{ message: string }`. Ответ возвращается как SSE-поток. Клиент читает поток через `fetch()` + `ReadableStream` reader (стандартный `EventSource` не поддерживает POST), парсит SSE-кадры и дописывает чанки к текущему сообщению аналитика в реальном времени.
  - Сохранение: сообщение пользователя сохраняется в `ChatMessage` (role=USER) до начала стриминга. Полный ответ аналитика сохраняется в `ChatMessage` (role=ASSISTANT) после успешного завершения стрима. При обрыве соединения частичный ответ НЕ сохраняется — при перезагрузке страницы пользователь увидит только своё сообщение без ответа.
  - Системный промпт: читается из файла `.claude/agents/analyst.md` при каждом запросе, передаётся как системное сообщение в вызов модели. В БД не сохраняется (role=SYSTEM зарезервирован, но в MVP-0 не используется для персистентности).
  - Контекст модели: системный промпт + вся история диалога (USER + ASSISTANT) из `ChatMessage`. Без RAG — загруженные файлы в контекст не подмешиваются (Task 2.1).
- **Scope**: mvp-0

## Background processes

В рамках Task 1.3 фоновых задач (очередей, воркеров, cron) нет. Ответ модели стримится синхронно из route handler-а — Next.js приложение не делегирует долгую работу в воркер, потому что стриминг — это не «долгая работа» в смысле платформенного инварианта (ответ идёт клиенту в реальном времени, а не считается в фоне). Очередь `spec:generate` и связанные воркеры — Task 2.1 и далее.

## Data entities

Изменение затрагивает одну модель в шаблоне проектной схемы (`packages/db/prisma/schema_project_template.prisma`):

- **ChatMessage** (обновлённая): id, role (`USER` | `ASSISTANT` | `SYSTEM`), content (`@db.Text`), tokensIn (`Int?`, новое), tokensOut (`Int?`, новое), createdAt, deletedAt. Индекс по `createdAt`.
  - `tokensIn` / `tokensOut` — количество входных и выходных токенов из ответа провайдера. Обнуляемые (`Int?`): стриминговый mock не всегда возвращает корректные значения, а обрыв соединения означает отсутствие финального chunk-а с метриками. Заполняются best-effort после завершения стрима.

Последствия изменения схемы:

- `schema_project_template.prisma` обновляется — новые проекты получают поля при создании.
- Существующие проектные схемы (созданные до этого изменения) требуют `ALTER TABLE`. Для dev-окружения допустимо пересоздание проекта; для прод-миграции — отдельный скрипт обновления (см. Assumptions).

Остальные модели проектной схемы (`Specification`, `Task`, `UserFile`, `Document`, и т.д.) в Task 1.3 не затрагиваются — они есть в шаблоне, но не имеют потребителей.

## APIs and integrations

### REST: `POST /api/projects/[id]/chat`

- **Auth**: `requireUser()` → `canAccessProject(user.id, projectId)`. При отсутствии доступа — 404 (без раскрытия существования проекта, по конвенции).
- **Request body**: `{ "message": string }`. Пустая строка после trim → 400.
- **Response**: `Content-Type: text/event-stream`. SSE-кадры:
  - Текстовый чанк: `data: {"content":"..."}\n\n` — для каждого фрагмента ответа модели.
  - Завершение: `data: [DONE]\n\n` — после полного ответа и его сохранения в БД.
  - Ошибка: `event: error\ndata: {"message":"..."}\n\n` — при сбое вызова модели или иной ошибке. Стрим после этого закрывается.
- **Порядок операций**: проверка auth → валидация тела → `getProjectClient(schemaName)` (по `schemaName` из `ProjectMeta`) → сохранение сообщения пользователя → чтение системного промпта из файла → загрузка истории диалога → вызов адаптера `chat()` → стриминг чанков клиенту → после завершения сохранение ответа ассистента (с `tokensIn`/`tokensOut` если доступны) → `[DONE]`.

### ModelRouter адаптер

Расположение: `packages/ai-roles/src/`. Пакет сейчас пустой стаб — Task 1.3 его наполняет.

Интерфейс:

```typescript
interface ChatMessage {
  role: 'USER' | 'ASSISTANT' | 'SYSTEM';
  content: string;
}

interface ChatConfig {
  model: string;
  apiKey?: string;
  systemPrompt: string;
}

interface ModelProvider {
  /** Стримит текст ответа чанками. Бросает исключение при ошибке. */
  chat(messages: ChatMessage[], config: ChatConfig): AsyncIterable<string>;
}
```

- Поставляется одна реализация: `ZaiProvider`.
- **ZaiProvider (гибридный)**:
  - Если `process.env.ZAI_API_KEY` задан — реальный HTTP-вызов к z.ai API (модель GLM), со стримингом ответа. Возвращает чанки текста как `AsyncIterable<string>`.
  - Если `ZAI_API_KEY` отсутствует — локальный mock: возвращает эхо-ответ (повторяет или парафразит сообщение пользователя) или заранее подготовленный ответ из фиксированного набора. Mock также стримит (с небольшой задержкой между чанками) — чтобы клиентский код пути стриминга был тем же. Это позволяет вести локальную разработку без внешнего API.
  - Mock помечает `tokensIn`/`tokensOut` как `null` или расчётной оценкой; реальный путь извлекает значения из финального chunk-а ответа z.ai.
- **Конфигурация в MVP-0**: `ChatConfig` формируется route handler-ом из переменных окружения (модель по умолчанию, `ZAI_API_KEY`), а не из БД — экран ModelConfig и таблица `ModelConfig` появляются в Task 2.3.
- **Fallback и кеш**: НЕ реализуются. Интерфейс `ModelProvider` спроектирован так, чтобы позже можно было добавить регистрацию нескольких провайдеров и оркестрацию, но MVP-0 не содержит этой логики.

### Системный промпт

Файл `.claude/agents/analyst.md` читается из файловой системы при обработке каждого запроса. Путь вычисляется относительно корня репозитория. Файл не копируется в БД и не кешируется — изменения в нём применяются со следующего запроса без перезапуска. Содержимое передаётся как единственное сообщение с `role: 'SYSTEM'` в начало массива `messages` вызова адаптера.

## AI agents and automation

- **Агент «Аналитик» (вариант MVP-0)**: проводит интервью с пользователем, помогая превратить идею в спецификацию. Источники знаний: только системный промпт (`.claude/agents/analyst.md`) и история диалога из `ChatMessage`. ## Non-functional requirements

- **Platform**: веб, интегрируется в существующее Next.js App Router приложение. Адаптивность: ниже 768 px левая панель свороваривается, чат занимает полную ширину (по конвенции платформы).
- **Stack**: Next.js App Router (route handler для SSE), React 18 (server + client components), Tailwind v4 (`@theme` токены из `@aiflow/ui/styles/theme.css`). FSD-структура: новый feature-слайс `features/chat/` с barrel `index.ts`; маршрут в `app/(app)/projects/[id]/research/`; API — в `app/api/projects/[id]/chat/route.ts`. Адаптер — в `packages/ai-roles/src/`.
- **Архитектурные соответствия**:
  - `app/` — только маршрутизация; вся логика — в feature-слайсах и пакетах.
  - Auth: `requireUser()` + `canAccessProject()` в route handler-е, по паттерну `app/api/projects/route.ts`.
  - Доступ к данным: через `getProjectClient(schemaName)` из `@aiflow/db`; прямых обращений к БД из route handler-а нет — через feature-сервис (`listMessages`, `saveMessage`).
  - Публичный surface feature-слайса — через `index.ts`; глубокие пути блокируются линтером (`import/no-internal-modules`).
- **Design**: минималистичный, светлая тема, акцентный синий `#2563EB` (токены платформы). Аватары пользователя и аналитика визуально различимы. Toast-ы сверху-справа: успех зелёный, ошибка красный (по конвенции `09-ui-spec.md`).
- **SSE-реализация**: route handler возвращает `Response` с `ReadableStream`. Клиент читает через `fetch()` + `getReader()` (не `EventSource`, т.к. POST). Парсинг SSE-кадров — на стороне клиента.
- **Тестирование**: Vitest. Сервисный слой (`listMessages`, `saveMessage`) покрывается unit-тестами с замоканным Prisma-клиентом. ZaiProvider покрывается тестами для обоих путей (mock + реальный, последний — с замоканным HTTP). SSE-формат — тест на route handler с замоканным адаптером.
- **Constraints**: размер файла ≤ 200 строк, функция ≤ 50 строк, сложность ≤ 10 (ESLint warn → блокирует в CI, по `15-engineering-conventions.md § 3`).

## Assumptions and open questions

Принятые решения (зафиксированы, чтобы не пересматривать):

1. **Расположение адаптера.** ModelRouter-адаптер живёт в `packages/ai-roles/src/` (не отдельный пакет). Пакет уже объявлен в code-map для этой роли.
2. **Гибридный провайдер z.ai.** Единственный провайдер в MVP-0. Реальный HTTP при наличии `ZAI_API_KEY`, локальный mock — без неё. Оба пути возвращают `AsyncIterable<string>` и покрыты тестами.
3. **Системный промпт из файла.** `.claude/agents/analyst.md` читается в рантайме при каждом запросе. Не кешируется, не хранится в БД.
4. **Формат SSE зафиксирован.** `data: {"content":"..."}\n\n` для чанков, `data: [DONE]\n\n` для завершения, `event: error\ndata: {"message":"..."}\n\n` для ошибок. Без количества токенов в стриме.
5. **Стратегия сохранения.** Сообщение пользователя — до стрима. Полный ответ ассистента — после завершения стрима. При обрыве частичный ответ не сохраняется и не виден после перезагрузки.
6. **tokensIn / tokensOut добавлены в схему сейчас.** Nullable (`Int?`), заполняются best-effort.
7. **Нет RAG в Task 1.3.** Контекст модели — системный промпт + история диалога. Загруженные файлы в MVP-0 в контекст не попадают.
8. **Нет fallback и кеша.** Интерфейс `ModelProvider` их закладывает, но реализация MVP-0 — ровно один провайдер без оркестрации.

Открытые вопросы (требуют решения до или в ходе планирования):

9. **Build-vs-adopt для UI чата.** Пользователь поднял вопрос: зачем писать чат с нуля, если есть готовые решения. Перед Planner-ом стоит задача — исследовать существующие React chat UI библиотеки с пермиссивными лицензиями (MIT/Apache) и принять решение: принять готовую или писать кастом. Кандидаты к исследованию: `assistant-ui`, наборы chat-компонентов. Функциональные требования выше написаны библиотеко-независимо (описано что UI делает, а не как построен) — чтобы Planner мог превратить build-vs-adopt в конкретную задачу. Проверка лицензий — по процессу `15-engineering-conventions.md § 8`.

10. **Миграция существующих проектных схем.** Добавление `tokensIn` / `tokensOut` в шаблон означает, что новые проекты получают поля, а существующие — нет. Для dev-окружения допустимо пересоздание. Нужен ли одноразовый скрипт `ALTER TABLE` для прод-проектов, или это решается в рамках общего механизма обновления проектных схем (в code-map отмечен как отложенный)?

11. **Согласованность полей ChatMessage со старой SPEC.** `specs/ai-studio/SPEC.md` (Data entities) уже упоминает `tokensIn`, `tokensOut` для ChatMessage, а Prisma-шаблон их не имел — расхождение закрыто в этом Task 1.3. После внесения изменений стоит обновить датап-модель-док (`docs/03-data-model.md`) и code-map (`docs/16-code-map.md`), отметив что `packages/ai-roles` и feature-слайс `features/chat` перестали быть пустыми/объявленными.

12. **Поведение кнопки «Создать спецификацию».** В MVP-0 это UI-заглушка. Точное поведение при нажатии (ничего / toast / disabled-состояние) — на усмотрение реализации; должно быть очевидно пользователю, что генерация пока недоступна.
